# quzzar-backend

Backend conventions. Repo-wide rules (naming, file organization, error handling, formatting) live
in `quzzar-workplace`. Read that too.

## When to use

- Writing or changing an API route, handler, edge function, or service function.
- Touching the database: queries, schema, RLS policies, or migrations.
- Adding auth, validation, a workflow, or an external integration.
- Anything involving secrets or deploy configuration.

## First: read the repo's own context

Read the applicable repository instructions, starting with `AGENTS.md`, and inspect the
project configuration for its runtime, database, and commands. Honor other instruction
files used by the active agent. Repo facts beat general preferences below.

## Rust-first implementation

Use Rust with Cargo for backend and reusable application logic by default. Read the bundled
`rust-skills` index and the relevant rule files before Rust work. Keep business logic in
reusable crates with thin service and Tauri bindings so the same implementation serves
browser and native consumers.

Use TypeScript with Bun or Python with uv when their runtime or ecosystem is needed. Follow
`quzzar-workplace` for shared-source architecture and language selection. Supabase is the
preferred managed database/auth/storage platform; select tools for concrete requirements
rather than treating the stack as a closed allowlist.

## Languages and runtimes

- **Bun**: runtime *and* package manager for TypeScript services and JavaScript workspace tooling.
  **Never npm.**
- **Deno**: TypeScript where the host requires it, such as Supabase edge functions.
- **Python + uv**: use `uv sync` for dependencies and `uv run` for commands.
- **Rust + Cargo**: compile and run Rust services, workers, and libraries with Cargo.

Check which context you're in before writing a runtime-specific import or a lockfile-touching
command. Code written for one does not necessarily run on the other.

## Rust backend work

Apply `quzzar-workplace` language selection before choosing a language. For Rust components:

- Model valid states with structs and enums, and expected failures with `Result`. Propagate or
  handle errors; reserve panics for broken internal invariants rather than ordinary failures.
- Prefer safe Rust. Any `unsafe` needs a concrete necessity, documented safety invariants,
  and focused review and tests.
- Use the compiler and Clippy feedback while developing, then test behavior and failure paths.
  Run `cargo fmt --check`, `cargo clippy`, and `cargo test` with the repo's workspace, target,
  and feature settings. Benchmark the relevant workload when performance motivates the choice.
- Choose a crate, binary, or service boundary that fits the existing system. Check deployment
  and integration support before committing to it, and preserve the existing authorization,
  database write path, API response shape, and observability.

## Shared contracts across languages and runtimes

For TypeScript consumers, cross-boundary shapes are Zod schemas in the shared schema package:
wire shapes, intake, agent contracts, and form validation via the RHF resolver. Objects are
**parsed** at the boundary, not cast (core guideline 4). Types are derived from schemas.

At a Rust or Python boundary, maintain one authoritative wire contract with native types and
runtime validation in each consumer. Generate bindings where practical and cover compatibility
with contract tests. Deserialization alone does not enforce business constraints. Preserve the
same field names and `ApiResponse` serialization across languages.

Two things bite when one TypeScript package is consumed as source by Bun and Deno:

- **Relative imports need explicit `.ts` extensions**. Deno rejects extensionless imports, and
  every tsc consumer then needs `allowImportingTsExtensions`. Type-check against *both* runtimes
  after touching the shared package, not just the one you're working in.
- **If a bundler can't reach outside its workdir**, the schemas get copied in-tree instead.
  That copy is a **build artifact**: gitignored, generated by a script, never hand-edited and
  never reviewed. A fresh checkout needs the sync run before type-checking will pass.

## Authorization and database access

**Use RLS for user-scoped reads and writes.** Enable RLS on exposed tables and grant only the
operations each role needs. Define SELECT, INSERT, UPDATE, and DELETE policies as applicable,
including both existing-row access (`USING`) and allowed resulting values (`WITH CHECK`).
Test ownership and tenant boundaries, not merely whether an authenticated request succeeds.

Route mutations through the application/API boundary when business logic calls for it while
preserving user-scoped database authorization. A server-side route does not require a
service-role database client. With Supabase's Data API, carry the verified user's JWT so RLS
runs under that identity. For direct Postgres connections, use a restricted role and correctly
established transaction-local identity; database owners, superusers, and BYPASSRLS roles can
bypass policies. Never assume a Rust backend or installed RLS policies alone prove enforcement.

Reserve elevated service-role access for explicit trusted server-side needs, such as an
administrative or background operation that cannot run with user-scoped permissions. Record
why elevation is needed, enforce authorization and scope at that boundary, and test denied
cases. Service-role access bypasses RLS; do not make it the universal write path.

Browser and Tauri installations are distributed clients. Neither may contain a service-role
key, database credential, AI provider secret, or Langfuse secret. Local Rust code in a native
binary does not make embedded credentials server-side secrets.

Use privileged database functions only when necessary, with constrained privileges, safe
search paths, and explicit authorization checks. Verify any intended RLS bypass as a separate
security boundary rather than treating it as an ordinary query.

Primary reference: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Enforce invariants in Postgres

Limits, capacity, and uniqueness belong in the database (BEFORE triggers with advisory locks,
partial unique indexes), not only in application code. Application checks race; the database
doesn't.

The API layer's job is to *map* a database rejection onto a good response (core guideline 5:
a limit hit is `fail`, the client's fault, not `error`).

**Keep a repeatable access test** covering the permission matrix, limits, and lockdown, and run
it after *any* schema, RLS, or permission-function change. Policy changes are the class of edit
where "it looks right" is worth least.

## Migrations

Migrations are reviewed like code, and must be safe to deploy *before* the code that uses them.

For live data, expand additively first: add the required tables/columns and preserve structures
that deployed consumers still use. Build and verify RLS, contracts/endpoints, required services,
typed clients, and UI integration before the new path is released.

Track after-live data migration and destructive removal separately. Specify source/destination
fields, rollout/cutover dependencies, consistency checks, and the condition for each deletion.
Once the new path is live and the agreed prerequisites hold, migrate and reconcile the data,
then delete superseded structures and compatibility code in a reviewed cleanup change.
Do not retain dead structures indefinitely or drop them while deployed consumers still need
them. Follow the project's promotion process and production authorization.

When using `quzzar-system-design`, read its `references/implementation-order.md` for stage
checks and the expand/release/migrate/contract sequence. New systems without live data need
no invented compatibility phase. Additive DDL alone is not proof of zero downtime; inspect
the actual locking, data volume, constraints, and deployment overlap.

## Orchestration

Use Temporal when the work actually needs durable long-running orchestration. Do not add it
for ordinary requests or simple jobs. Choose its integration with the Rust-first backend
against the deployment/runtime requirements rather than assuming an SDK is available.

When separate pipelines need isolated workers, give them independently controlled entry
points and queues so stopping one cannot accidentally stop unrelated work.

## API design

Every response follows the `ApiResponse<T, F>` shape from `quzzar-workplace` core guideline 5.
The three-way split is load-bearing: `success`, `fail` (client's fault: validation and business
rules, per-field in `data`), `error` (server's fault: `message` safe to surface, never leaking
internals).

## Config and secrets

- Secrets live in gitignored local env files and as platform secrets in production.
  **Never in the frontend bundle.**
- **Rotate anything that gets pasted into a chat, ticket, or PR.** Treat exposure as having
  happened, not as a risk to assess.
- Each runtime and each host reads secrets differently. When adding one, account for every place
  it has to exist (local, CI, and the deploy target), or it will fail in exactly the one you
  forgot.

## Deploy

Verify deploy configuration explicitly rather than trusting defaults. A per-function auth
setting that defaults the wrong way will silently gateway-lock a function on its *next* deploy,
long after the change that caused it.

**Smoke-test after deploying.** An unauthenticated request should return your handler's own
response, not the platform's. That distinction is what tells you the function is actually
reachable.

## Observability

**Instrument every application AI/model call with Langfuse**, including Rust, TypeScript,
and Python callers, background tasks, and the trusted service behind browser/native clients.
Use a shared instrumented integration per provider rather than scattered untraced calls.
Capture model/provider identity, timing, outcome, and usage/cost when available, linked to
the surrounding operation. Add quality scores where applicable. Verify trace delivery with
a representative call; configuration alone is not evidence that tracing works.

Use a supported SDK or Langfuse's documented OpenTelemetry ingestion for the chosen runtime.
Check current integration documentation; do not invent Rust SDK support or add a Python/JS
service solely to emit traces. Keep instrumentation/export credentials in trusted services.

Never put PII, tokens, or full request payloads in traces or logs. Capture safe metadata and
redacted content as appropriate. Ordinary application failures still need logging outside AI
traces. See [Langfuse integrations](https://langfuse.com/integrations).

## Testing

Playwright for end-to-end tests against a running app, per `quzzar-workplace`. Rust logic also
uses Cargo unit and integration tests; Python tests run through uv using the repo's test runner.

Note the gap: an e2e-first tool only reaches backend surface exposed through a request path.
Workflows, activities, and permission policies that no request touches need their own coverage.
The access test above is part of that answer.

## Rules

- Rust/Cargo is the default; use supporting languages and infrastructure for concrete needs.
- Use the language and runtime guidance above for commands and dependency changes.
- User reads and writes use RLS; elevated access is an explicit, tested server-side boundary.
- Every application AI/model call is traced with Langfuse.
- Invariants belong in Postgres, not only in application code.
- Validate cross-boundary shapes against the shared contract in each language.
- Every response is `ApiResponse<T, F>`. `fail` is the client's fault, `error` is ours.
- Rotate any secret that gets pasted anywhere.
- Repository instructions and actual project configuration override general preferences here.
- Deleting an unused endpoint means deleting its schema, tests, types, and policies too
  (core guideline 1).
